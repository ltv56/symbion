# Database schema

MySQL 8, InnoDB, utf8mb4. Migrations are hand-written SQL in `apps/api/src/migrations/`.

## merchants

| Column         | Type                | Notes                                                      |
| -------------- | ------------------- | ---------------------------------------------------------- |
| `id`           | BIGINT UNSIGNED, PK | auto increment                                             |
| `name`         | VARCHAR(255)        |                                                            |
| `api_key_hash` | CHAR(64), UNIQUE    | SHA-256 hex digest (64 chars); the raw key is never stored |
| `created_at`   | TIMESTAMP           | defaults to now                                            |

API keys are 32 random bytes (64 hex chars) generated by `POST /merchants` and returned once in that response. SHA-256 is enough because the key has 256 bits of entropy, and the hash must be deterministic so the key can be looked up by its unique hash. `POST /merchants` is unauthenticated until admin auth is added.

## tiers

Global: managed by the app admin, shared by all merchants (no `merchant_id`).

| Column       | Type                 | Notes                                                   |
| ------------ | -------------------- | ------------------------------------------------------- |
| `id`         | BIGINT UNSIGNED, PK  | auto increment                                          |
| `name`       | VARCHAR(255), UNIQUE | e.g. silver, gold                                       |
| `min_points` | INT UNSIGNED         | threshold to reach this tier                            |
| `earn_rate`  | DECIMAL(5,2)         | points per currency unit; DECIMAL avoids float rounding |

## members

Points are shared across merchants, so `email` is unique across the whole programme.

| Column        | Type                 | Notes                                                    |
| ------------- | -------------------- | -------------------------------------------------------- |
| `id`          | BIGINT UNSIGNED, PK  | auto increment                                           |
| `merchant_id` | BIGINT UNSIGNED, FK  | `merchants(id)`; the merchant where the member signed up |
| `tier_id`     | BIGINT UNSIGNED, FK  | `tiers(id)`                                              |
| `email`       | VARCHAR(255), UNIQUE |                                                          |
| `name`        | VARCHAR(255), null   |                                                          |
| `created_at`  | TIMESTAMP            | defaults to now                                          |

No auth columns yet: members are identified by email for the demo. `POST /members` requires the merchant's `x-api-key` header (SHA-256 of the key is matched against `merchants.api_key_hash`) and sets `merchant_id` from it; the request body no longer carries `merchantId`.

## orders

| Column            | Type                | Notes                                 |
| ----------------- | ------------------- | ------------------------------------- |
| `id`              | BIGINT UNSIGNED, PK | auto increment                        |
| `merchant_id`     | BIGINT UNSIGNED, FK | `merchants(id)`; set from the API key |
| `member_id`       | BIGINT UNSIGNED, FK | `members(id)`                         |
| `idempotency_key` | VARCHAR(255)        | chosen by the merchant per order      |
| `amount`          | DECIMAL(12,2)       | DECIMAL avoids float rounding         |
| `created_at`      | TIMESTAMP           | defaults to now                       |

`UNIQUE (merchant_id, idempotency_key)` (`uq_orders_merchant_idempotency_key`) is the last line of defence against duplicate orders. `idempotency_key` uses the binary collation `utf8mb4_bin`, so keys that differ only by case are different orders (the default collation would treat them as equal). It is scoped per merchant, so two merchants may reuse the same key.
